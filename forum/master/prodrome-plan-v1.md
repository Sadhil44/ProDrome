Prodrome, project plan v1 (condensed from README.md, PRD.md and SETUP.md; re-scope and re-assign freely, but announce it in crosstalk/decisions when you do).

IDEA. Predict, diagnose and heal Kubernetes workloads before they fail. Kubernetes already self-heals, but only reactively and only one way: a health probe fails, the pod restarts. It cannot tell a memory leak from a CPU spike from a saturated connection pool, so it applies the same blunt fix to all three, and it waits until users are already affected. Prodrome adds lead time and diagnosis: it watches workloads, forecasts that one is heading for failure, classifies what kind of failure, and applies the matching remediation through the Kubernetes API - measured against stock Kubernetes on identical faults.

WHY NOT JUST AUTOSCALE. Production predictive scaling (AWS, Google) and RL autoscalers share one property: a single lever, scale up or down. That is why none of them need diagnosis. Prodrome's action space has several levers where the wrong choice is actively harmful. Memory leak: Kubernetes restarts, which is correct by accident. CPU saturation under load: Kubernetes restarts, which removes capacity mid-saturation; the correct action is scale out. Connection-pool exhaustion: Kubernetes restarts; the correct action is shed load, because scaling adds connections and worsens it. Disk pressure: Kubernetes restarts, which changes nothing; the correct action is alert. Once scaling stops being the only option, "how much" becomes "which", and a system with no diagnosis has no basis for answering it.

HOW IT WORKS. Four stages, per workload, on each 15-second scrape.
1. Detector - is this abnormal and heading for failure? Unsupervised, trained on healthy data ONLY. Real failures cannot be enumerated in advance, and injected faults are step functions while real degradation is a slide, so training on injected faults just teaches the model to recognise the injector. Outputs a score and a yes/no; if it says no, nothing downstream happens. It is the gate.
2. Classifier - what kind of failure? Supervised, trained on injected faults, over a window of WINDOW_SIZE ticks by the canonical metric order. Returns a label and a confidence.
3. Policy - what do we do, and are we sure enough? A hand-written lookup table, deliberately not learned, because an operator must be able to answer "why did this restart my pod at 3am". Per-action confidence thresholds, because being wrong costs different amounts per action: the cheap hedging action unlocks at low confidence, the expensive one only as the diagnosis firms up. Below the floor everything becomes UNKNOWN and nothing happens. Rationale: PRD.md section 7.2.
4. Controller - execute it through the Kubernetes API, in shadow mode until the safety rails are verified, writing one decision-log row per evaluation.

THE CONTRACTS (SETUP.md section 7). These schemas are the only things that need agreement across pairs; everything else is an implementation detail its owner can change freely. Changing one requires telling everyone.
- Metrics table, Parquet, one row per workload per 15 s tick: ts, workload, cpu_cores, mem_bytes, mem_pct, net_rx, net_tx, fs_reads, fs_writes, restarts. workload is a stable name (redis, not redis-7d9f8b-x2k1).
- Labels table, CSV, one row per injected fault: start_ts, end_ts, workload, fault_type, pattern, run_id. run_id is required; train/test splits are by run, never by row.
- Decision log, CSV, one row per controller evaluation: ts, workload, detector_score, fired, predicted_class, confidence, top_features, action, result, mode.

FILES, NOT SERVICES (SETUP.md section 8). Workstreams exchange files, not HTTP calls. data/healthy/metrics.parquet: written by collect, read by signal. data/chaos/metrics.parquet plus labels.csv: written by collect, read by diagnosis. The fitted detector: written by signal, read by cluster. The fitted classifier: written by diagnosis, read by cluster. data/decisions/log.csv: written by cluster, read by collect. No ports, no service discovery, no debugging someone else's process. If someone's output is not ready, fall back to data/samples/ and keep working. Nobody waits.

THE KNOWN SAFETY GAP. Held out an entire fault class from training and asked what the model does with a fault it has never seen: it correctly abstained on none of the novel-fault windows, and was confidently wrong (above the policy table's bar) on a quarter of them. Those windows would trigger a real remediation for a fault the model does not understand. That is a safety gap, not a data artifact, and it is the argument for the open-set recognition work in the later phases. Anyone touching thresholds or the classifier should know this number.

GROUND RULES (SETUP.md section 10). Each one prevents a specific way of producing results that look good and mean nothing.
1. The detector never trains on injected faults.
2. Split train/test by run, never by row - consecutive windows overlap by 19 of 20 ticks, and a random split puts near-duplicates on both sides. If accuracy exceeds ~0.97, assume this bug and check.
3. Label the full fault trajectory, not just the peak, including the faint early windows - otherwise the classifier only recognises faults that are already catastrophic, and fails exactly where the detector fires.
4. Every claim ships with the control-arm comparison.
5. Build the simple baseline first; if the simple version ties, ship it and say so.
6. Report per fault type, never one aggregate - an average hides the cases where the method does not work, and those are the most informative part.
7. Say what it cannot do: instant failures get no warning, no cross-service root cause, closed label set. Stating these is what makes everything else credible.
8. If it is not reproducible from a fresh clone, it is not a result.
The standing question for every change: what is the baseline, and did you beat it?

RISKS. Classifying injected faults is close to trivial (a CPU stressor spikes CPU, a memory stressor spikes memory), so a high accuracy number proves little on its own - the lead-time curve and the control-arm comparison are the results that mean something. Synthetic data that is flat teaches the detector that normal means flat, so it fires on the first genuine traffic change; synthetic faults that jump straight to full intensity never show the model what a slide toward failure looks like. The classifier is confidently wrong on unseen fault classes. Everyone runs their own disposable kind cluster on purpose: sharing one creates a queue, and a queue means people wait.

NON-GOALS. No cross-service root cause analysis. No log or trace analysis - metrics only. Not a general replacement for the horizontal autoscaler. No hosted service. No claim of novelty: this is a reimplementation and extension of published research, and says so.
